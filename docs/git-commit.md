# Git 提交规则

本文件适用于在本仓库工作的 AI 工具。编写提交消息或执行 Git 提交前，必须先阅读本文件。通用协作约定见根目录 [AGENTS.md](../AGENTS.md)，本文件只维护 Git 提交相关规则。

## 提交授权与范围

- 只有用户明确要求提交时，才执行 `git commit`；要求编写提交消息不代表授权提交。
- 提交前检查工作区及暂存区，只提交用户授权范围内、本次任务相关的文件，保留用户和其他协作者的改动。
- 不默认执行 `git add .`，按文件选择暂存；同一文件混有无关改动时，按改动块选择暂存。
- 不将已有暂存内容视为本次提交授权；发现无关暂存内容时，不擅自提交或取消暂存，先确认范围。
- 未经用户明确要求，不执行 push、amend、rebase 或强制推送。
- 不提交密钥、个人配置、依赖目录、临时日志和测试数据。
- 对仓库已跟踪且用于部署的 `.min` 资源，源文件变更并按 [部署文档](deploy.md#后台公共-js--css-压缩资源更新) 要求重新构建时，应将实际变化的压缩资源与源文件一起提交；其他生成物仍遵守根目录 AGENTS.md 的限制。

> 当前仓库尚无上述 `docs/deploy.md` 及对应章节，引用按提供的规则保留，待补充部署约定后使用。

## 提交消息

- 默认使用简体中文，技术名称、路径和标识符保持原样。
- 根据实际提交的 diff 自动编写消息；用户已指定消息时，遵循用户要求。
- 格式为：`类型(范围): 改动摘要`，范围可省略。
- 范围使用清楚的模块名称，例如 `h5`、`backend`、`deploy`。

| 类型 | 用途 |
| --- | --- |
| `feat` | 新增功能 |
| `fix` | 修复问题 |
| `refactor` | 不改变业务行为的重构 |
| `docs` | 仅修改文档 |
| `style` | 仅格式调整 |
| `test` | 测试相关 |
| `build` | 构建及依赖调整 |
| `chore` | 其他维护 |

- 标题简洁，准确描述最终改动，不使用“修改代码”“修复 bugs”等模糊表述。
- 简单改动只写标题；跨模块改动增加正文，说明主要变化和必要原因。
- 消息以实际提交内容为准，不把方案、待办或未验证事项写成已完成。
- 文档记录了某项方案时，应写“补充方案文档”，不能写成已实现该功能。
- 提交消息只描述改动，不加入 AI、编辑器或代理的作者信息。禁止 `Co-authored-by`、`Signed-off-by`、`Generated-by` 等署名行，以及工具名称、邮箱和生成标记。

示例：

```text
fix(h5): 统一货币符号展示并优化日语分集编号
```

## 提交前检查与交付

1. 检查工作区、暂存区和实际 diff，确认提交范围。
2. 根据改动范围执行必要检查，如实说明未执行或失败的检查；已有有效验证且代码未变时，不无故重复运行。
3. 检查暂存 diff，确认没有无关文件、敏感信息或意外生成物。
4. 提交时使用实际换行组织多行消息；通过命令行传入复杂正文时，优先使用临时消息文件和 `git commit -F`，避免转义改变内容。
5. 提交后核对完整消息，包括标题、正文和 trailer。若发现 AI 或工具署名被自动追加，且该提交由本次操作创建、尚未推送，只从消息中移除该行；不得为此修改 Git 用户配置，也不得跳过钩子。报告提交哈希、提交标题和验证结果；没有执行 push 时不得声称已推送。
